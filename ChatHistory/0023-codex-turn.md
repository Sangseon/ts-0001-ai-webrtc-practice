기존 마이크 트랙이 예상치 못하게 종료됐다면 성공으로 표시하지 말고 실제 상태를 확인해주세요.

사용자 조작이 실패하면 실제 장치·SFU 상태에 맞게 UI를 복구하거나 오류 상태를 명확히 표시해주세요.

상태 이름과 자료구조는 기존 코드에 맞춰 최소한으로 설계해주세요.

## 6. UI 구현

기존 `MediaPanel` 및 관련 컴포넌트에 필요한 제어 기능을 추가해주세요.

### 6.1. 로컬 제어

- 카메라 ON/OFF 버튼
- 마이크 음소거·해제 버튼
- 현재 카메라 송신 여부
- 현재 마이크 음소거 여부
- 연결 및 처리 중 상태
- 장치 권한·획득 실패 안내

기존 로컬 미디어 획득/종료 버튼과 SFU 연결/종료 버튼의 역할을 명확히 구분합니다.

사용자가 회의에서 카메라만 끄는 동작으로 전체 미디어 연결이나 마이크 송신을 종료하지 않도록 해주세요.

처리 중 중복 클릭이 발생해도 중복 트랙과 Producer가 생성되지 않아야 합니다.

### 6.2. 원격 참가자 표시

다른 참가자가 카메라를 끈 경우:

- 이전 영상이 계속 활성 상태로 표시되지 않음
- 기존 participantId와 프로필 유지
- 아바타 또는 카메라 OFF 상태 표시
- 마이크가 켜져 있으면 해당 참가자의 오디오는 유지

다른 참가자가 마이크를 음소거한 경우:

- 참가자별 음소거 상태 표시
- 실제 서버 송신 상태와 일치
- 카메라 화면은 유지

다시 켜거나 음소거를 해제하면 정상 상태로 갱신해주세요.

기존 RemoteMedia의 참가자별 그룹과 공통 프로필 구조를 재사용합니다.

카메라를 껐을 때 단순히 Video Consumer가 없어졌다는 이유로 참가자 전체를 삭제하여 음소거 상태까지 소실하지 않도록 검토해주세요.

수신 전용 참가자와 논리적 회의방 참가자의 상태 표시도 구분합니다.

이번 Step에서는 참가자 UI의 대규모 재설계는 하지 않습니다.

## 7. Signaling과 서버 검증

기존 WebSocket 및 SFU Signaling 계약을 확인한 후 필요한 최소 메시지만 확장해주세요.

다음 항목을 검토합니다.

- 카메라 Video Producer 개별 종료
- 새로운 Video Producer 생성
- Audio Producer pause
- Audio Producer resume
- 원격 참가자에게 상태 변경 전달
- 신규 Producer 및 Producer 종료 이벤트 재사용
- 요청 실패와 실제 상태 동기화

서버는 기존 세션의 participantId를 기준으로 다음 관계를 검증해주세요.

- 요청자의 실제 WebSocket 세션
- 현재 활성 mediaId 및 roomId
- 해당 회의방 소속
- Producer 소유권
- Producer의 실제 kind
- Producer의 현재 활성·종료·pause 상태
- 다른 참가자의 Producer 접근 차단

존재하지 않는 Producer, 종료된 Producer, 과거 mediaId 및 다른 참가자 소유 Producer에 대한 제어 요청을 안전하게 거절해야 합니다.

기존 4,096-byte WebSocket payload 제한, 네트워크 입력 검증 및 오류 응답 정책을 유지합니다.

마이크 상태 전파는 Consumer 전체 재생성보다 기존 Consumer와 상태 동기화를 재사용하는 방식을 우선 검토해주세요.

현재 mediasoup API가 제공하는 pause/resume 이벤트와 브라우저 측 상태 반영의 차이를 확인하고, 실제 동작을 검증해주세요.

## 8. 비동기 경합 및 자원 정리

다음 상황을 검증해주세요.

1. 카메라 OFF → ON 반복
2. 카메라 ON 처리 중 OFF 클릭
3. 카메라 획득 중 회의 연결 종료

5. Video Producer 생성 직후 종료

7. 음소거 요청 중 WebSocket 종료

필요하다면 같은 미디어 종류의 제어 요청을 직렬화하거나 처리 중 중복 요청을 제한합니다.

사용자의 최종 의도와 실제 장치·Producer 상태가 불일치하지 않도록 해주세요.

늦게 도착한 작업의 성공 응답이 이미 종료된 연결을 다시 활성화하지 않아야 합니다.

기존 Step 09의 종료 및 자원 정리 로직을 훼손하지 마세요.

## 9. 다중 회의방 정책 검증

A는 1111과 2222에 모두 소속되어 있고, 활성 미디어 회의방은 1111이라고 가정합니다.

다음 동작을 확인해주세요.

- 1111에서 카메라 OFF
- 1111에서 마이크 음소거
- 2222 채팅 화면으로 이동
- 1111의 기존 미디어 연결 유지
- 2222에는 별도 Producer·Consumer가 생성되지 않음
- 1111에서 카메라 ON 및 마이크 음소거 해제
- 1111 원격 참가자에게 상태 변경 반영
- 2222 채팅 정상 송수신

이후 A가 활성 미디어 회의방을 2222로 명시적으로 변경하는 상황도 확인해주세요.

- 1111의 Send/Recv Transport 및 Consumer 정리
- 로컬 트랙 재사용 가능 여부 확인
- 2222의 미디어 연결 생성
- 카메라 OFF 및 마이크 음소거 상태의 처리 정책 명시
- 이전 연결의 늦은 상태 변경이 새 연결에 적용되지 않음

특히 음소거 상태가 회의방 전환 과정에서 의도치 않게 해제되어 음성이 송신되지 않도록 해주세요.

회의방 전환 시 사용자 제어 상태를 유지할지 초기화할지 현재 프로젝트의 트랙 소유권 정책을 확인하고, **명시적인 해제 동작 없이 음소거가 자동 해제되지 않는 안전한 방향**을 우선 검토해주세요.

단일 활성 미디어 회의방 정책을 유지합니다.

## 10. 3인 브라우저 자동화 검증

Step 09에서 구현한 Chrome·Edge 독립 프로필과 가상 장치 테스트 구조를 재사용해주세요.

A·B·C가 같은 회의방에서 Audio/Video를 송수신하는 상태를 구성합니다.

### 10.1. 카메라 OFF

A의 카메라를 끄고 다음을 확인합니다.

- A의 로컬 비디오 트랙 종료
- B·C의 A Video Consumer 정리
- B·C에서 A의 이전 영상 비활성화
- A의 Audio Producer 유지
- A와 B·C 사이의 오디오 연결 유지
- A가 수신하는 B·C 미디어 유지

### 10.2. 카메라 ON

A의 카메라를 다시 켜고 다음을 확인합니다.

- 실제 새로운 비디오 트랙 생성
- 새로운 Video Producer 생성
- B·C가 새로운 Producer 발견
- B·C의 새로운 Consumer 생성
- 실제 RTP 수신 증가
- 비디오 프레임 디코딩 증가
- 중복 비디오 Consumer 없음

### 10.3. 마이크 음소거

A의 마이크를 음소거하고 확인합니다.

- Audio Producer 유지
- Pause 상태 적용
- 로컬 오디오 트랙 상태 동기화
- B·C에 음소거 상태 표시
- SFU에서 A의 오디오 송신 일시 중지 확인
- 실제 오디오 전달 중단 여부 확인
- A의 Video Producer 및 수신 연결 유지

음소거 상태는 단순히 오디오 패킷 수치가 짧은 시간 변하지 않았다는 사실만으로 판단하지 마세요.

Producer pause 상태, 원격 Consumer 상태 및 실제 송수신 통계를 함께 검증해주세요.

테스트 구간과 통계 측정의 한계도 명시합니다.

### 10.4. 마이크 음소거 해제

A의 음소거를 해제하고 확인합니다.

- 기존 Audio Producer 재개
- 가능하다면 Audio Producer ID 유지
- 로컬 Audio Track 정상 활성화
- B·C에서 상태 표시 갱신
- SFU를 경유한 RTP 수신 재개
- 불필요한 새 Audio Producer 생성 없음

### 10.5. 반복 및 교차 조작

다음 시나리오를 실행해주세요.

- 카메라 OFF/ON 5회 이상
- 마이크 음소거/해제 5회 이상
- 카메라 OFF 상태에서 마이크 음소거·해제
- 음소거 상태에서 카메라 OFF/ON
- 두 참가자가 서로 다른 종류의 제어를 동시에 수행
- 빠른 연속 클릭
- 제어 중 참가자 퇴장
- 제어 중 미디어 회의방 전환
