# Step 14 — 후속 개발 계획과 QC·QA 기준 문서화

## 목적과 범위

[Step 13](./Step13.md)은 Step 01~12의 기능과 자동화 검증을 종합했지만, WebSocket 테스트 러너 비종료·과거 Signaling timeout 간헐 실패의 원인은 남았고 실제 물리 장치 인수도 수행하지 않았다. 기존 구현 계획과 그 결과를 보존하면서 코드 품질을 확인할 기준과 사용자가 직접 기능을 인수할 절차가 필요했다.

Step 14는 [PLAN](./PLAN.md)에 Step 14 이후 후속 작업을 정식 번호로 추가하고, [QC](./QC.md)·[QA](./QA.md) 작업 문서를 만드는 **계획·문서화 단계**다. 제품 코드의 품질 점검, 사용자 수동 QA, 코드 개선이나 새 기능 구현은 이 단계에서 수행하지 않았다.

## QC 문서 구성

[QC.md](./QC.md)는 Step 01~13 구현의 설계·유지보수성을 검토하기 위한 **코드 품질 점검표**다. 현재 QC-001~QC-026, 총 **26개 항목**을 프로젝트 구성, TypeScript 품질, TypeScript/CommonJS 혼용, WebSocket·서버, WebRTC·SFU, 클라이언트 미디어, 테스트 코드, 알려진 문제 영역으로 나눈다. 각 행에는 관련 Step, 점검 항목·기대 기준, 확인 대상·방법, 결과·발견 문제·심각도, 개선 필요 여부·대상 Step을 기록한다.

`확인`은 사용자가 관리하는 품질 점검 상태다. `-`는 확인 전, `점검 필요`는 문제·의심 사항의 추가 확인 또는 개선 필요, `정상`은 실제 품질 점검에서 기대 기준을 충족했다는 뜻이다. 별도의 `결과`는 PASS / FAIL / PARTIAL / BLOCKED / NOT RUN이라는 기존 검증 판정이다. 자동화 테스트 통과나 파일 존재만으로 `확인: 정상`으로 바꾸지 않는다. 결함은 `QC-DEF-001` 같은 ID와 근거·개선 Step으로 연결한다.

현재 26개 항목의 `확인`은 모두 `-`다. 일부 `결과` 칸에는 Step 13 등의 정적 사실과 알려진 문제로 PARTIAL이 기록돼 있으나, **QC 전체의 실제 코드 품질 검수는 수행되지 않았다.** 이 두 상태를 같은 완료 표시로 취급하지 않는다.

## QA 문서 구성

[QA.md](./QA.md)는 사용자가 Windows·Chrome·Edge에서 Step 01~13 기능을 직접 확인하기 위한 **시나리오 기반 인수 절차**다. QA-001~QA-026, 총 **26개 케이스**에 사전 조건, 재현 가능한 실행 절차, 예상 결과, 공식 판정, 증빙, 결함 ID, 비고와 여러 줄로 작성할 수 있는 독립된 실제 결과 영역을 둔다.

QA의 `확인`도 `- / 점검 필요 / 정상`이다. 이때 `정상`은 사용자가 실제 테스트를 수행해 예상 결과를 충족했다는 의미이며 자동화 성공만으로 부여하지 않는다. `판정`은 PASS / FAIL / BLOCKED / NOT RUN으로 별도 기록한다. 오류가 발견되면 `QA-DEF-001` 형식의 결함 ID와 화면·로그·RTP 수치 등 증빙을 연결한다.

현재 26개 케이스는 모두 `확인: -`, `판정: NOT RUN`, 실제 결과 `미기입`이다. 집계표 역시 NOT RUN **26개**로 시작한다. Step 13의 가상 장치·자동화 결과는 수동 QA PASS나 물리 카메라·마이크 인수 결과가 아니다.

## Step 14~20 후속 계획

[PLAN.md의 후속 섹션](./PLAN.md)은 기존 Step 01~13을 소급 변경하지 않고 다음 작업을 연속 번호로 관리한다.

| Step | 작업 | 이 단계와의 관계 |
| --- | --- | --- |
| 14 | 후속 계획·QC/QA 기준 | **문서 작성 완료**. 실제 검수는 미착수 |
| 15 | 언어 혼용·구조 QC와 최소 개선 | QC 항목에 실제 코드·타입 검사 근거를 채우고 필요한 작은 개선 수행 |
| 16 | 테스트 안정성·종료 정리 | WebSocket 러너 비종료와 Signaling timeout 간헐 실패 조사 |
| 17 | 화면 구조·사용자 흐름 설계 | 논리 방·채팅 화면·활성 미디어 방을 구분하는 설계 |

| 20 | 확인 결함 보완과 프로젝트 마무리 | Step 19에서 재현한 결함만 수정·재검증하고 최종 문서 정리 |

Step 15~20은 모두 미착수이며 사용자가 각각 명시적으로 요청할 때 진행한다. **Step 14는 검수 기준을 작성한 단계이고, 실제 전체 QC·QA 수행 단계는 Step 19다.**

## 문서 검증과 완료 판정

로컬 파일과 Git 이력에서 QC·QA 문서 생성, 각 26개 ID, PLAN의 Step 14~20 정의, README의 QC·QA 상대 링크를 확인했다. QC는 GitHub 표의 열 수와 셀 구분자를 맞추는 후속 수정이 있었고, QA는 항목별 `확인`과 독립된 실제 결과 영역을 갖춘 현재 형식이다. 이 문서 자체의 링크·Markdown 구조는 작성 후 정적으로 확인한다. 실제 GitHub 화면 렌더링과 사용자 수동 QA 실행을 완료했다는 의미는 아니다.

**Step 14 완료 기준:** 후속 계획과 QC·QA 문서의 작성·구조 확인은 완료. 실제 QC 코드 점검과 QA 사용자 인수는 미수행이므로 프로젝트 전체 인수 완료는 보류한다. Step 13에서 기록한 최초 실패·재실행 이력과 물리 인수 보류도 그대로 유지한다.
