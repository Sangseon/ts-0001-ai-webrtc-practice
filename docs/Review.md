# Vibe Coding Review

이번 프로젝트에서는 Codex를 활용해 TypeScript 기반 WebRTC SFU 화상회의를 구현하면서 바이브 코딩을 경험했다.

## 화면 설계와 프롬프트

프롬프트에 요구사항과 컨벤션을 상세하게 작성하더라도, 화면 구성은 글보다 이미지로 전달하는 것이 빠르고 정확하다고 느꼈다.

실제 UI 구현 과정에서도 의도한 화면과 결과물 사이에 차이가 있었다. 초기부터 스토리보드나 와이어프레임을 준비했다면 불필요한 수정과 의사소통을 줄일 수 있었을 것 같다.

## 프로젝트 구조와 컨벤션

프로젝트 초기에 디렉터리 구조와 코드 구성 기준을 정하는 것도 중요했다.

별도의 구조 컨벤션 없이 구현을 진행하다 보니 `src` 아래에 파일이 계속 추가됐다. AI가 코드를 빠르게 생성하는 만큼, 프로젝트가 커지기 전에 개발자가 이해하고 관리할 수 있는 구조를 먼저 정할 필요가 있다고 느꼈다.

## 구현 속도와 코드 이해

구현 속도는 확실히 빨랐다.

WebRTC P2P는 이전에 구현한 경험이 있어 직접 개발하더라도 비교적 빠르게 진행할 수 있었겠지만, SFU 방식은 구조를 학습하고 구현 시 주의할 점과 자원 관리 방법 등을 확인하는 데 상당한 시간이 필요했을 것이다.

AI의 도움으로 구현을 빠르게 진행하면서 익숙하지 않은 기술의 구조와 동작을 이해하는 데 집중할 수 있었다.

다만 **구현 속도가 빨라진다고 개발자의 코드 이해 속도까지 빨라지는 것은 아니었다.** 생성된 코드를 이해하고 검토하는 과정은 여전히 필요했다.

## 작업 범위와 검증

단계별로 작업 범위와 완료 기준을 명확하게 정하는 것이 중요했다. 단순히 기능 구현을 요청하는 것보다 기존 기능의 유지 조건과 검증 기준을 함께 전달했을 때 작업 결과를 확인하기 수월했다.

또한 자동화 테스트를 통과했다고 해서 실제 환경에서도 모든 기능이 정상 동작하는 것은 아니었다. 실제 마이크 테스트에서는 자동화 과정에서 발견하지 못한 문제가 확인됐다.

이 경험을 통해 AI가 작성한 코드와 테스트 결과를 그대로 신뢰하기보다, 개발자가 직접 동작을 확인하고 문제를 판단하는 과정이 필요하다고 느꼈다.

## 마무리

이번 프로젝트를 통해 AI는 익숙하지 않은 기술을 학습하고 구현하는 데 충분히 유용한 도구라는 것을 경험했다.

하지만 원하는 동작을 정의하고, 프로젝트 구조와 작업 방향을 결정하며, 구현 결과의 적절성을 판단하는 것은 여전히 개발자의 역할이었다.

**AI를 통해 구현에 드는 시간은 줄일 수 있었지만, 설계와 검증, 최종 기술적 판단은 개발자의 몫이라는 점을 다시 확인했다.**
