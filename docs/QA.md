# QA — Step 01~13 사용자 기능 인수 절차

## 준비와 판정 규칙

이 문서는 [Concept](./Concept.md)·[PLAN](./PLAN.md)의 기능을 **사용자가 직접 실행**해 확인하는 절차다. 코드 품질은 [QC](./QC.md), 기존 자동화 실행 결과는 [Step13](./Step13.md)에 따로 기록한다. **이번 문서 작성 중 아래 수동 QA는 실행하지 않았다.** 각 케이스의 실제 결과·증빙·결함 ID는 실행자가 채운다.

Windows 11, Node.js 24, npm 12, Chrome·Edge의 독립된 프로필/시크릿 창을 준비한다. A·B·C는 서로 다른 브라우저 세션이고 D는 방 격리 확인용이다. 실제 상대 음성·영상 인수는 가능하면 서로 다른 사람·PC와 헤드셋을 사용한다. 현재 PC에는 물리 웹캠이 없으므로 해당 항목은 실행 시 `BLOCKED`로 기록하고 가상 장치 성공으로 대체하지 않는다. 다른 PC의 일반 HTTP 사설 IP는 카메라 권한을 보장하지 않으므로 보안 컨텍스트·SFU 접근 주소를 먼저 확인한다. 권한·장치 상태는 테스트 전에 되돌릴 수 있는 방법을 기록하고 운영체제 설정을 무리하게 변경하지 않는다.

저장소 루트에서 PowerShell 터미널 두 개를 연다. 최초 설치가 필요하면 `npm ci`; 이후 터미널 1에서 `npm run dev:server`, 터미널 2에서 `npm run dev:client`를 실행한다. `Invoke-RestMethod http://127.0.0.1:3000/health`와 `http://127.0.0.1:5173` 접근을 확인한다. 테스트 종료 시 두 터미널에서 Ctrl+C로 종료하고 `Get-NetTCPConnection -State Listen | Where-Object { $_.LocalPort -in 3000,5173 }`로 남은 리스너를 확인한다. 개발 서버 외 브라우저·worker를 강제 종료할 때는 본인이 시작한 프로세스만 대상으로 한다.

판정은 `PASS`(실제 기대 결과 확인), `FAIL`(재현 가능한 불일치), `BLOCKED`(장치·권한·환경 부족), `NOT RUN`(미실행)이다. 일부 단계만 끝났다면 전체 케이스는 `NOT RUN` 또는 `BLOCKED`로 두고 비고에 수행 범위를 적는다. 증빙에는 날짜·OS/브라우저·Git 커밋·세션 A/B/C·장치 종류·화면 캡처/콘솔/RTP 수치·실행 명령과 종료 코드를 적는다. 결함은 `QA-DEF-001`처럼 번호를 부여하고 재현 절차, 예상/실제 차이, 빈도, 로그, 영향을 받는 방/참가자를 남긴다. 개인 음성·영상 녹화는 필수 증빙이 아니며 동의 없이 수집하지 않는다.

아래 각 카드에는 `QA ID / 관련 Step / 기능명 / 목적 / 사전 조건 / 실행 절차 / 예상 결과 / 실제 결과 / 판정 / 증빙 / 결함 ID / 비고`가 있다. 실행 후 마지막 다섯 필드를 채운다. **초기 상태는 전부 NOT RUN**이다. 수동 QA 전체 인수는 [PLAN 통합 인수 표](./PLAN.md)의 항목과 아래 케이스가 실제 근거로 PASS이고 치명적 결함이 없을 때만 선언한다. 물리 장치 또는 LAN 항목이 BLOCKED라면 전체 인수는 보류한다.

### QA-014 · Step 08 · 수신 전용·재생 제한
- **목적 / 사전 조건:** 로컬 미디어 없이 명시적 수신 / A 송신 중, B 로컬 미디어 미획득.

### QA-025 · Step 13 · 연결·권한 오류 후 재사용

- **실행 절차:** 1. 테스트 세션에서 장치 권한 거부·없는 장치 선택으로 오류 확인하고 다른 세션의 채팅·방 상태가 유지되는지 확인. 2. 허용/장치 복구 후 명시적으로 다시 시작. 3. 개발 서버를 종료·재시작하고 각 세션에서 `다시 연결`, 방 재입장·미디어 재연결 확인.
