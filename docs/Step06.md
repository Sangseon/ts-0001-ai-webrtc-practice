# Step 06 — 로컬 카메라·마이크 획득과 미리보기

2026-10-30 Windows, Node.js 24.22.1, npm 12.2.1에서 구현했다. 현재 정책은 카메라만·마이크만·두 종류 모두의 선택형 획득이다. Chrome·Edge 가상 장치와 Mock 검증은 통과했고, 이후 사용자 수동 검증에서 실제 이어폰 마이크만 획득하는 데 성공했다. 물리 웹캠 검증은 남아 있어 전체 완료는 보류한다. 초기 동시 획득 기록, 선택형 가상 자동화, 선택형 사용자 수동 결과를 아래에 구분한다.

## 목적과 범위

사용자가 획득할 종류를 선택하고 시작 버튼을 눌렀을 때 해당 기본 장치만 요청한다. 카메라가 선택된 경우 로컬 영상, 모든 경우 실제 획득한 트랙 상태를 표시한다. 종료·해제·늦은 응답 시 소유 트랙과 video 참조를 정리한다. 미디어 없이 방 입장·채팅을 이용할 수 있고 방마다 스트림을 복제하지 않는다.

SFU Signaling·송수신, Transport·Producer·Consumer, 원격 영상, 음소거·카메라 개별 제어, 장치 목록·선택, 입력 레벨, 저장·업로드는 이번 범위에 없다. 기존 서버 코드와 프로토콜은 변경하지 않았다.

## 환경과 API 조건

기존 TypeScript 7.0.2 strict 설정의 `DOM`, `DOM.Iterable` lib가 MediaDevices·MediaStream·MediaStreamTrack·HTMLVideoElement 타입을 제공한다. React 19.3.1·Vite 8.3.5를 그대로 사용하며 새 패키지는 없다.

실행 파일에서 확인한 브라우저 버전은 Chrome 156.0.8078.49, Edge 156.0.4314.50이다.

`getUserMedia`는 보안 컨텍스트와 권한이 필요하다. HTTP의 `localhost` 및 루프백 `127.0.0.1`은 로컬 개발에서 신뢰 가능한 출처로 취급된다. 일반 사설 IP의 HTTP까지 같은 조건이라고 가정하지 않는다. 다른 PC에서 접근하려면 HTTPS 등 별도 조건을 검토해야 한다. [W3C Secure Contexts](https://w3c.github.io/webappsec-secure-contexts/#is-origin-trustworthy)

앱은 시작할 때 `window.isSecureContext`와 `navigator.mediaDevices?.getUserMedia`를 확인한다. Chrome·Edge 가상 장치 테스트에서 두 로컬 주소의 실제 API 노출과 미디어 획득을 확인했다. 실제 브라우저·OS 권한 설정은 변경하지 않았다.

## 획득과 미리보기

1. 카메라·마이크 체크박스를 선택한 뒤 명시적으로 시작할 때만 요청한다. 카메라만은 `{video:true,audio:false}`, 마이크만은 `{video:false,audio:true}`, 둘은 `{video:true,audio:true}`다. 모두 미선택이면 시작 버튼이 비활성화되고 Hook도 API 호출 없이 반환한다.
2. 요청한 종류의 live 트랙만 필수로 검증하고 요청하지 않은 종류가 반환되면 정리 후 실패 처리한다. 동시 요청의 일부만 반환되면 전체를 정리하며, 자동 단일 장치 fallback 대신 사용자가 종료·재선택·재시작한다. 요청 중·사용 중 선택은 잠가 진행 중인 요청의 조건이 바뀌지 않게 한다.
3. MediaStream은 트랙 묶음이고 각 MediaStreamTrack은 오디오 또는 비디오 소스의 생명주기를 나타낸다. 실제 객체는 Ref로 관리하고 State에는 status·error·트랙 ID/kind/readyState 스냅샷만 둔다.
4. 카메라 선택 시만 video.srcObject에 연결하고 muted·autoPlay·playsInline을 적용해 play 성공 후 ready로 표시한다. 마이크만이면 video는 숨기고 srcObject=null을 유지하며 play를 호출하지 않는다. 마이크를 다른 재생 요소나 스피커에 연결하지 않는다.

동시 요청은 두 종류를 모두 만족해야 하지만 단일 요청은 선택하지 않은 종류가 없어도 진행할 수 있다. 선택한 장치 자체의 부재·권한·접근 오류는 계속 실패로 처리한다. [W3C Media Capture and Streams](https://w3c.github.io/mediacapture-main/#dom-mediadevices-getusermedia)

상태는 idle → requesting → ready, 오류이면 error, 권한 대기 중 종료를 누르면 stopping으로 표시한다. pending Ref로 동기 중복 요청을 막고 State로 버튼을 비활성화한다. 미디어 오류는 컴포넌트 안에 표시해 기존 채팅 요청 오류와 섞이지 않는다.

## 소유권·종료·비동기 경합

- `streamRef`는 현재 소유한 스트림 하나다. `videoRef`는 화면의 video이며, 별도의 attachedVideo Ref는 React가 DOM Ref를 먼저 비운 뒤에도 해제 대상 요소를 참조한다. 요청 ID·generation·mounted Ref는 화면 표시와 구분한다.
- 종료와 해제 시 트랙 ended 리스너를 제거하고 video를 pause·srcObject=null로 해제한 다음 모든 트랙을 stop한다. 첫 stop이 예외여도 나머지 트랙을 계속 시도한다.
- 정상 stop 후 readyState를 직접 읽어 ended 상태를 화면에 남긴다. stop은 ended 이벤트를 발생시키지 않으므로 이벤트를 기다리지 않는다. 다른 탭 등에서 같은 장치를 사용한다면 앱의 트랙 종료와 하드웨어 전체 전원 해제는 같지 않다. [Media Capture 트랙 종료 규칙](https://w3c.github.io/mediacapture-main/#dom-mediastreamtrack-stop)
- 비정상 ended 이벤트는 장치 중단으로 안내하고 남은 트랙도 종료한다. stop 중 실패하거나 여전히 live인 트랙이 있으면 정리 실패를 성공으로 표시하지 않는다.
- 권한 요청은 AbortSignal로 취소할 수 없다. 종료·해제로 generation을 바꾸고, 늦게 받은 결과의 세대가 다르면 video에 연결하지 않고 즉시 모든 트랙을 stop한다.
- 권한 요청 또는 play가 끝나기 전에는 후속 시작을 막는다. 종료 후 브라우저가 아직 권한 응답을 기다리면 stopping을 유지한다. 권한 창을 무시해 Promise가 끝나지 않으면 새 요청도 계속 대기한다. 임의 timeout으로 추가 장치 요청을 생성하지 않는다.
- 컴포넌트 해제 후에는 State를 갱신하지 않는다. 진행 중이던 play 완료·실패도 이전 세대이면 새 상태를 덮어쓰지 않는다.
- 정상 종료 뒤 재시작은 새 스트림을 획득한다. WebSocket 종료는 미디어를 자동 중지하지 않고, 미디어 종료도 연결·방·채팅을 끊지 않는다. 장치 사용 종료는 미디어 종료 버튼 또는 컴포넌트 해제로 수행한다.

## 오류 정책

| 조건 | 처리 |
| --- | --- |
| NotAllowedError | 권한 또는 OS·브라우저·페이지 정책 확인 안내. 무조건 사용자 거부로 단정하지 않음 |
| NotFoundError | 요청한 카메라 또는 마이크를 찾지 못했음을 안내하고 선택한 종류를 확인하도록 안내. 선택하지 않은 장치까지 없다고 단정하지 않음 |
| NotReadableError | 다른 프로그램 사용·장치/OS 접근 상태 안내 |
| OverconstrainedError | 조건을 만족하는 장치 부재 안내 |
| AbortError·SecurityError | 브라우저 중단·보안 정책 안내 |
| API 미지원·비보안 컨텍스트 | 획득 호출 전 각각 별도 안내 |
| play 실패 | video 참조와 획득한 트랙 정리 후 재시작 안내 |
| 비정상 ended | 전체 소유 스트림 정리 후 장치·권한 확인 안내 |
| 알 수 없는 오류 | 획득·재생 실패 안내, 기존 연결 기능 유지 |

실패 후에도 사용자가 다시 시작할 수 있다. 권한 우회·자동 설정 변경·특정 deviceId 요청은 구현하지 않았다. DOMException의 분류는 [getUserMedia 명세](https://w3c.github.io/mediacapture-main/#dom-mediadevices-getusermedia)를 기준으로 삼았다.

## 정책 변경 전 사용자 실제 브라우저 수동 검증 결과

다음 내용은 사용자가 전달한 개발 PC 환경과 수동 실행 결과다. Codex가 물리 장치로 직접 재실행한 결과가 아니다.

| 항목 | 사용자 보고와 확인 범위 |
| --- | --- |
| 물리 장치 환경 | 물리 웹캠 없음, 이어폰 마이크만 연결 |
| 실행 | 실제 브라우저에서 로컬 미디어 시작 실행 |
| 획득 결과 | 카메라·마이크 동시 획득 실패 |
| 실제 영상 미리보기 | 획득에 실패해 미검증 |
| 실제 트랙 종료·재획득 | 성공한 스트림이 확인되지 않아 미검증. 실패를 근거로 트랙 stop·장치 해제 성공을 주장하지 않음 |
| 이어폰 마이크 개별 획득 | 미검증. 마이크 연결 사실은 audio-only getUserMedia 성공을 뜻하지 않음 |
| 실제 오류·권한 정보 | 브라우저 종류·버전, DOMException name/message 원문과 권한 응답은 이번 사용자 보고에 포함되지 않음 |

당시 앱은 `{video:true,audio:true}`만 요청했고 웹캠 부재는 그 실패 조건과 일치했다. 오류 원문이나 마이크 접근 결과를 확보하지 않았으므로 이어폰 마이크가 없거나 사용할 수 없다고 판단하지 않았다. 이 표의 마이크 개별 획득 미검증 상태는 당시 기록이며, 선택형 변경 후의 성공 결과는 다음 절에 기록한다.

당시에는 NotFoundError 안내에 동시 요청임을 덧붙였다. 현재는 “요청한 카메라 또는 마이크를 찾을 수 없습니다. 선택한 종류의 장치 연결 및 사용 가능 여부를 확인해주세요.”로 변경했다. 오류 하나로 어느 장치가 부족한지 또는 두 종류가 모두 없는지를 확정하지 않는다.

## 선택형 정책 변경 후 사용자 수동 검증

다음은 사용자가 실제 개발 PC의 브라우저에서 수행해 전달한 결과다. Codex가 물리 장치로 직접 실행한 결과나 Chrome·Edge 가상 장치 자동화 결과와 구분한다. 이번 보고의 수동 브라우저 종류·버전과 상세 트랙 로그는 제공되지 않았다.

| 항목 | 사용자 수동 검증 결과 |
| --- | --- |
| 물리 환경 | 물리 웹캠 없음, 이어폰 마이크 연결 |
| 마이크만 선택 | 실제 이어폰 마이크 획득 성공 |
| 카메라만 선택 | 장치 없음 오류 정상 표시. 카메라 획득 성공이나 영상 미리보기 성공을 뜻하지 않음 |
| 미디어 없는 참여 | 미디어를 사용하지 않아도 회의방 참여 및 채팅 가능 |
| 로컬 미디어 종료 | UI가 “시작 전 / 종료됨” 상태로 전환됨 |
| 실제 트랙 종료 근거 | UI 전환은 확인했으나 readyState=ended·stop 호출·장치 사용 해제의 직접 확인은 이번 보고에 없어 미검증으로 유지 |
| 물리 카메라·영상·동시 획득 | 웹캠 부재로 카메라 획득 성공·영상 미리보기·물리 두 장치 동시 획득 미검증 |

마이크만 사용하는 물리 환경의 획득 성공과 미디어 없는 참여는 수동 근거가 추가됐다. 가상 장치에서 확인한 트랙 ended·video.srcObject=null·재획득 성공을 이 수동 실행의 확인 결과로 옮겨 적지 않는다. 실제 권한 거부·반복 재시도·하드웨어 종료 확인도 보고된 범위 이상으로 완료 처리하지 않는다.

### 경미한 UI 개선 사항

NotFoundError 발생 후 미디어 종류 선택을 변경해도 이전 오류 메시지가 남는 현상이 사용자 수동 검증에서 보고됐다. 선택 상태와 이전 시도의 오류 안내를 명확히 구분하기 위한 경미한 UI 개선 사항으로 기록한다. 이번 문서 반영에서는 오류 자동 초기화 등 코드를 추가하지 않았다.

## 선택형 정책 변경과 가상 장치 자동화 검증

카메라·마이크 체크박스로 획득할 종류를 명시한다. 기본 체크 상태는 두 종류이며 시작 전 자유롭게 바꿀 수 있다. 요청 중·사용 중에는 선택을 잠그고 종료 후 다시 선택한다. 이는 획득 전 미디어 종류 선택이며 특정 deviceId·장치 전환이나 송신 중 카메라 ON/OFF·음소거 구현이 아니다.

| 선택 | 실제 getUserMedia 조건 | 획득·표시 |
| --- | --- | --- |
| 카메라만 | video:true, audio:false | 비디오 live, 음소거 영상 미리보기 |
| 마이크만 | video:false, audio:true | 오디오 live, video.srcObject=null, 로컬 음성 재생 없음 |
| 카메라+마이크 | video:true, audio:true | 두 종류 live, 음소거 영상 미리보기 |
| 모두 미선택 | API 호출 없음 | 시작 비활성화, 방·채팅 이용 가능 |

요청 조건은 호출 시 복사해 고정하고, 선택한 종류만 필수로 검사한다. 단일 종류 요청은 다른 종류의 트랙을 요구하지 않는다. 실제 반환된 모든 트랙을 종료 대상으로 삼고, 예상하지 않은 종류나 필수 종류가 없는 반환 스트림은 전체 정리 후 실패 처리한다. 기존 요청 세대·중복 시작·늦은 응답·해제·재생 완료 경합 처리는 유지한다.

## 물리 장치 수동 인수 절차

현재 PC에서 이어폰 마이크 단독 획득과 종료 UI 전환은 사용자 수동 확인이 끝났다. 아래 절차 중 실제 트랙 ended·장치 사용 해제와 반복 재시도 확인은 남아 있다. 카메라만·동시 획득 성공의 물리 검증에는 웹캠을 준비해야 한다. 가상 장치 테스트 통과를 물리 검증 완료로 대체하지 않는다.

1. 실제 카메라·마이크를 준비하고 가상 장치 플래그가 없는 일반 Chrome 또는 Edge에서 개발 화면을 연다. 시작 전 앱의 장치 사용이 없는지 확인한다.
2. 먼저 마이크만 체크하고 시작한다. 실제 권한 요청 범위와 오디오 트랙 live, video 참조 없음·로컬 음성 미재생을 확인한다. 웹캠 준비 후 카메라만과 두 종류도 각각 실행해 선택한 트랙만 live인지 확인한다. 영상 선택 시 본인 영상이 움직이고 음소거인지 확인한다.
3. 종료를 눌러 실제 획득한 트랙의 ended와 영상 참조 제거를 확인한다. 같은 장치를 사용하는 다른 앱·탭이 없다면 브라우저의 장치 사용 표시도 확인한다. 하드웨어 표시등은 다른 소비자 상태에 따라 별도 판단한다.
4. 시작·종료를 세 번 반복하고 새 트랙 ID와 이전 트랙 ended를 확인한다. 방 입장·채팅 화면 전환·닉네임 변경만으로 미디어를 다시 획득하지 않는지도 확인한다.
5. 새 사이트 권한 상태의 브라우저 프로필에서 실제 거부를 선택해 안내와 채팅 유지 여부를 확인한다. 재허용을 위해 설정 변경이 필요하면 사용자가 직접 수행한 뒤 재시도한다. 앱은 이를 강제로 바꾸지 않는다.
6. 가능하면 카메라 또는 마이크를 연결하지 않은 상태, 다른 프로그램이 장치를 독점하는 상태, 사용 중 장치 분리도 확인한다. 브라우저 오류명이 하드웨어 원인과 항상 일대일 대응한다고 단정하지 않는다.
7. 권한 요청 중 종료를 누른 뒤 늦게 허용한다. 미리보기가 살아나지 않고 반환 트랙이 종료되는지 확인한다. 요청 중 페이지 이동·닫기 후 장치 사용 해제도 확인한다.
8. Chrome과 Edge 각각 결과·장치 종류·권한 응답·미확인 항목을 이 문서에 추가한다. 사람이 직접 확인할 수 없는 마이크 입력 품질은 Step 12 수준계 구현 없이 트랙 확보만으로 검증했다고 표시하지 않는다.

선택형 정책 변경 전 작업에서는 NotFoundError가 카메라·마이크 모두의 부재를 단정하지 않는지 단위 테스트를 추가했고 당시 동시 획득 조건은 유지했다. 아래 표는 그 이전 작업의 결과이며 최신 선택형 결과는 위 별도 절을 따른다.

## 선택 이유·제약·Step 07 고려사항

브라우저 기본 API와 작은 Hook을 선택해 WebSocket에 미디어 소유권을 결합하지 않았다. 사용자가 종류를 명시적으로 선택하므로 마이크만 요청할 때 카메라를 자동으로 시도하지 않는다. 동시 요청 실패를 단일 종류로 자동 재시도하지도 않는다. 권한 대기를 취소할 API가 없어 종료 요청 뒤 대기하는 UX를 명시했다.

실제 장치 분리·OS 독점·사용자 권한 응답은 Mock으로만 확인했으며 실제 하드웨어 효과는 미검증이다. 다른 OS·Firefox·Safari·장시간 부하·HMR·빌드 preview의 미디어 재생은 검증하지 않았다. 트랙 muted/unmute 이벤트나 미디어 상태의 원격 동기화는 이후 범위다.

Step 07은 이 Hook이 소유한 현재 live 스트림을 송신 입력으로 연결할 수 있지만, 그 시점에 송신 중 stop·방 퇴장·연결 유실의 소유권 정책을 정해야 한다. 지금은 로컬 정리만 수행하고 Router·Transport·Producer를 만들지 않는다. 공유 자원을 선행 설계하지 않았다.

**판정:** PLAN의 선택형 완료 기준을 다시 확인했다. 실제 이어폰 마이크 단독 획득, 카메라 부재 오류 안내, 미디어 없는 방 참여·채팅, 종료 UI 전환은 사용자 수동 확인이 추가됐다. 그러나 물리 카메라 획득·영상 미리보기·동시 획득 성공, 실제 트랙 ended·장치 해제 직접 확인과 전체 권한·재시도 절차는 남아 있다. 따라서 Step 06 전체 완료는 계속 보류한다. Chrome·Edge 가상 장치에서 이미 통과한 항목은 별도 자동화 근거로 유지하며, 이번에는 docs/Step06.md만 수정하고 PLAN·소스·테스트는 변경하지 않았다. Step 01~05 완료 상태는 유지한다.
